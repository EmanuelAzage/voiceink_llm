* **Update**: Evaluated `gemma-4-31b-it` as a fallback for `gemini-3.5-flash-lite`'s rate limits — not adopted. A quick 3-transcript date-accuracy test looked perfect (9/9), but a broader pass with multi-item/messier transcripts (this app's actual core scenario) surfaced real schema corruption: a garbage `dueDate: "text:"` value and JSON-syntax fragments leaking into tags, in 3 of 4 tests, plus 3–7x slower responses. That garbage `dueDate` exposed a real validator gap — `validateExtractedCard` only checked `typeof dueDate === 'string'`, not that it was an actual well-formed date, so it would have silently passed through and broken notification scheduling downstream. Fixed with a new `isValidIsoDate()` in `src/services/date.ts`; a malformed date now drops just that field instead of rejecting the whole card. New tests in `date.test.ts` and expanded `cardSchema.test.ts`. See decisions.md for the full comparison data.

* **Decision correction, found by live-testing against the real API before trusting it**: Gemini's function-declaration `Schema` object rejects `additionalProperties` outright (HTTP 400 — "Unknown name additionalProperties: Cannot find field"), contradicting the original assumption in [decisions.md](decisions.md). Fixed by dropping the field from `cardJsonSchema`'s wire representation; `validateExtractedCard()` is the real `additionalProperties: false` enforcement point, not the schema sent over the wire. Worth remembering as a general lesson: don't ship a schema-format assumption for a third-party API without a live smoke test, even when the shape looks like standard OpenAPI/JSON Schema.
